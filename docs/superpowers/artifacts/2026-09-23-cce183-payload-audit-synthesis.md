CCE-183 is not "source-collector needs a cap." It is the third time the same defect has been paid for one field at a time: CCE-173 capped the citation digest so it stopped counting its own prose, CCE-176 *named* the next place uncapped text reached a reader (still Backlog — see Correction 1), and CCE-183 now asks for a cap on the Jira descriptions that overflowed a subagent's response. Each fix was correct and each one was applied downstream of a choke point that still measures nothing — so the defect simply reappeared somewhere else.

This repo's own CLAUDE.md names the pattern: three or more fixes each revealing a new problem in a different place is a wrong architecture, not a failed hypothesis. The architecture is wrong in one specific way. `scripts/orchestrator_runner.py:dispatch_validated` accepts an arbitrary `inputs` dict, hands it to `scripts/orchestrator_runner.py:dispatch_subagent`, which serializes it with a bare `json.dumps` into a single `-p` argv element — and nothing anywhere in the pipeline measures `len(prompt)` before the spawn. Twelve dispatch call sites across `scripts/orchestrator_runner.py` and `scripts/verify_runner.py` funnel through that one line. Bound it there, or keep paying per field forever.

## What the existing bounds actually protect

The split is stark, and it is the finding. Twenty-eight truncation sites exist across `scripts/`. **Twenty-seven of them bound a string that is displayed, logged, or reported. Exactly one bounds text reaching a subagent. Zero bound a schema-validated agent output.**

**Bounds on error, display and forensics strings (27):** `scripts/gh_client.py` clips gh stderr at 200 chars in seven separate `GhResult` error paths. `scripts/orchestrator_runner.py` defines `_STDERR_TRUNCATE = 300` and applies it at the git checkout, add and push failure sites and inside the CCE-141 diagnosis line. `scripts/lint/framework_build.py` clips mkdocs stderr at 500. `scripts/lint/citation_exists.py` clips one pathological token at `_MAX_REPORTED_TOKEN` — on the `OSError` arm only. `scripts/orchestrator_runner.py` truncates a forensics `input_preview` at 200 and the forensics call list at 50. `scripts/archive_indexes.py` clips an index summary at `_SUMMARY_MAX`. Every one of these is correct and none of them constrains a byte reaching a `claude -p` subprocess.

**Bounds on a real agent payload (1):** `scripts/state_io.py:load_voice_samples` caps at `cap = 20_000` chars total, slicing against a running budget across a list of sources, in deliberate priority order so the override survives intact, breaking out rather than emitting empty entries, and pinned by `tests/contracts/test_state_io.py`. It reaches three dispatch sites — page-author's nightly and bootstrap payloads and content-validator's. Note it is a **character** cap, not a byte cap: `json.dumps` defaults to `ensure_ascii=True`, so 20,000 chars of non-ASCII prose can serialize to ~120 KB. It is the only agent-payload bound in the repo and belongs in this census, but it is **not** the pattern to copy — see Correction 2. The character-vs-byte unit remains a real defect in it.

**Bounds on a schema-validated output (0):** confirmed by grep across all eight files in `agents/schemas/`.

One honest ambiguity: `_CITATION_FINDINGS_CAP` and `_CITATION_RUN_FINDINGS_CAP` are producer-side caps on reason strings, so they transitively bound both the PR body and the notifier payload — for one reason family. They are the closest thing in the repo to a payload bound that arrived by accident, and they are defeated by the adjacent uncapped `lint_block` writer that carries the same tokens.

## The fix

1. **Bound at `dispatch_validated`, the single choke point.** Twelve call sites across `scripts/orchestrator_runner.py` and `scripts/verify_runner.py` reach `dispatch_subagent`, which builds the prompt and hands it to `subprocess.run` as one argv element. Measure `len(prompt.encode())` there, before the spawn. Set the ceiling below Linux's 131,072-byte `MAX_ARG_STRLEN`, because that — not the ~1 MB `ARG_MAX` — is the limit on the platform the nightly actually runs on. In the same change, widen `except FileNotFoundError` to `except OSError`: today an oversized argv raises `OSError(E2BIG)` that escapes `dispatch_subagent`, escapes `run`'s `except`-less `try:`/`finally:`, and kills the process with a traceback — bypassing the entire CCE-144 classification system that exists to make failures loud.

2. **Declare each payload field fixed or elastic, with a deterministic trim order.** Fixed fields are small and load-bearing: SHAs, repo identity, lens names, `config_path`, `plugin_root`, `target_path`, `action`. Elastic fields are the external text: `pr.body`, `pr.files`, `jira_context[].description`, `summaries[].what_changed`/`why`/`notes`, `source_paths`, `cited_sources`, and every free-text member of `digest`. When a payload exceeds the ceiling, trim elastic fields in declared order until it fits, and say in the payload what was withheld — both halves of that pattern already exist in this repo, in `load_voice_samples` and in the `(+N more)` note the citation caps emit. Trimming the `pr.body` of a PR the agent is asked to summarize is a real loss, which is exactly why the order must be declared per agent at the call site rather than guessed globally.

3. **A coverage test mirroring `tests/orchestrator/test_classification_coverage.py`.** That test's mechanism is an AST walk, and it has three parts you should copy in full. First, `_add_partial_calls` parses the guarded module with `ast.parse`, walks for every `ast.Call` whose `func.id` or `func.attr` is `add_partial`, collects `{kw.arg for kw in node.keywords}`, and fails the test for any call site whose keyword set intersects neither `info_only` nor `degraded` — so relying on the runtime default is a test failure, not a silent inheritance. Second, a meta-test runs the same walk over a four-line fixture probe containing one bare call, one classified call, one advisory call and one attribute-style call, asserting the walk flags exactly two — so a green result means "all sites classified" and never "the walk found nothing". Third, a population tripwire asserts the exact call-site count with a comment block justifying every increment, so a new site cannot arrive unaudited. The payload analogue: walk every `dispatch_validated` / `dispatch_verified` call, read the keys of the `inputs` dict literal, and fail when a key carries no `fixed`/`elastic` disposition at that call site. **A registry was prototyped and rejected for the CCE-144 classification work** — that test's own docstring records why: keys built from the enclosing function plus a reason token collide in `verify_runner`, where three reason loops share a key but not a classification, and a registry decays as sites move. Requiring explicitness at the call site cannot decay. Do not build a central field-policy table; put the disposition where the field is.

4. **Reclassify overflow from blind to degraded, with a named reason.** A payload the orchestrator trimmed is the definition of CCE-144's degraded case: the run **held back** input it could not process. Record `payload_trimmed: <agent> <bytes>/<ceiling>` with `degraded=True`, so `scripts/orchestrator_runner.py:_should_advance_watermark` keeps the cursor honest through CCE-151's `held_back` set and the PR stays out of the advance rather than being consumed. Reserve blind for the case where the payload still exceeds the ceiling after every elastic field is trimmed to zero — that run genuinely cannot judge its input. Today neither outcome exists: below the OS limit the payload silently eats the agent's context and the failure surfaces as a schema error naming the wrong field, and above it the run dies outside the classification system entirely.

5. **Log the measured payload size every run.** One `info_only` reason per dispatch with the serialized byte count, and the run maximum in the step summary. The 2026-09-23 incident took an incident to diagnose because the failure surfaced as `schema_invalid: source-collector: 'prs' is a required property` — a missing-key error on a size problem. A single number per dispatch turns the next one into a graph instead of a forensic exercise, and it is the only way to choose the ceiling in item 1 from evidence rather than from a kernel constant.

## Tickets this subsumes

**Folds in.** CCE-183 becomes the architectural ticket and absorbs the per-field caps it would otherwise have spawned: the source-collector Jira and PR-body caps it was originally written for, plus the caps that would follow for `pr_summarizer` prose, `content_validator.failed[].message`, `fact_checker.findings[].claim`, `page_author.evidence.files_read` and `gap_detector.reasoning` — all of them are the choke-point bound applied N times at higher cost. CCE-173 and CCE-176 stay closed on their merits; cite them in the spec as the two prior instances that establish the pattern rather than reopening them. The `maxLength`/`maxItems` sweep across `agents/schemas/` folds in as defence in depth, with the explicit caveat that a schema cap fires only when the agent successfully emits a large-but-valid object — it would not have caught the 2026-09-23 run, which failed on a missing key. The `partial_reasons`/`lint_failures` duplicate key in the notifier digest folds in as a one-line free win.

**Stays separate.** CCE-144 and CCE-151 are unchanged — item 4 reuses their classification and their cursor, it does not alter either, and `tests/orchestrator/test_time_budget.py` and `tests/orchestrator/test_deferral_skip.py` must stay green byte-for-byte on the `time_budget_*` reason strings. The uncaught-`OSError` widening is bundled into item 1 only because it is the same three lines; if it slips, file it standalone, because it is a crash-outside-classification bug independent of any cap. Three defects found during the audit are not size problems and need their own tickets: `jira_lookup` subscripts `issue["key"]` on a schema-valid entry that may omit it; `v["reasoning"]` and `g['reasoning']` are read by bare subscript although `reasoning` is not in `gap_detector.schema.json`'s `required` list; and `scripts/orchestrator_runner.py:_pr_changed_files` reads `.path` while every archived real source-collector output keys file entries `filename`, so `grounding` — and therefore `source_paths` and the created page's `source_files` frontmatter — is silently empty on that arm. The whats-new rotation gap is a published-artifact problem, not a payload one; file it separately. CCE-127's App-token degradation is untouched.
